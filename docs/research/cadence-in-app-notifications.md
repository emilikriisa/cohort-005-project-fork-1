# Cadence in-app notification services: capability research

Observed: **2026-11-25**, Europe/Kiev. Primary-source documentation and public pricing only; no accounts provisioned, credentials used, purchases made, or live delivery tests performed. Links below were consulted on this date. Public pages can change; quoted prices are observations, not offers or forecasts.

Context: [Research third-party services for Cadence in-app notifications](https://github.com/emilikriisa/cohort-005-project-fork-1/issues/3), within [Map: specify actionable in-app notifications for Cadence](https://github.com/emilikriisa/cohort-005-project-fork-1/issues/1).

**Finding:** Knock, Novu Cloud (Notify), and SuprSend all expose the basic machinery for server-triggered, per-recipient in-app feeds with persistent engagement state and customizable React UI. They differ materially in retention, security configuration, pricing units, and plan gates. This report does **not** select a provider or make every researched feature a requirement.

Cadence's agreed scope is actionable in-app updates. Students, Instructors, Team Admins, and Platform Admins are candidate audiences; the event/audience matrix is still undecided. Per `GLOSSARY.md`, a Team Admin is a Student with a Team Licence responsibility. README's Knock setup suggestion is course context, not a provider commitment. No email migration, push, marketing, or production implementation is included.

Evidence labels: **D** = documented by the provider, **I** = integration inference, **U** = not established by this research. A documented capability is not proof that a particular installed SDK version or production configuration works.

**I — implications for Cadence:** map one stable account identity to one provider recipient; do not manufacture separate Student and Team Admin identities for the same person. Cadence must determine eligible recipients from its own permissions, deduplicate overlapping audiences, and reauthorize every linked action when opened. Provider tenant concepts need not map to Team Licences. A read notification does not mean its requested business action is complete. Sign tokens/hashes from the authenticated server session, never a client-supplied identity. These are proposed integration boundaries for later specification, not decisions resolving the audience or behavior tickets.

## Retries, idempotency, and delivery evidence

| Provider | Documented behavior | Remaining uncertainty / practical consequence |
| --- | --- | --- |
| Knock | `Idempotency-Key` deduplicates identical workflow-trigger requests for 24 hours; changed parameters produce an error. Support is specifically limited to the trigger endpoint. [API overview](https://docs.knock.app/api-reference/overview/api-keys) Delivery processing distinguishes retryable attempts from terminal failures and supports manual retry after fixing a failure. [Delivery](https://docs.knock.app/send-notifications/delivering-notifications) | **U:** no application-to-visible-feed latency/recovery guarantee was proven. Delivery-provider retry claims should not be substituted for Cadence-to-Knock request retry behavior. |
| Novu Cloud | API idempotency must be enabled for the organization; it is not universally on. API-key POST/PATCH requests support a key; successful/error responses cache for 24 hours and in-progress locks for five minutes. In-flight duplicates return 409. [Idempotency](https://docs.novu.co/api-reference/idempotency) `transactionId` is not equivalent API-level deduplication. [Trigger API](https://docs.novu.co/api-reference/events/trigger-event) | **D:** Inbox stores messages and sends websocket updates without an external delivery provider. External-channel send retries are absent, while Framework bridge calls have three retries; those are distinct paths. [Retry policy](https://docs.novu.co/platform/developer/delivery-retries) **U:** confirm enablement and test accepted-but-client-disconnected recovery. |
| SuprSend | Workflow `idempotency_key` suppresses repeat processing for 24 hours; strings up to 255 characters are supported. [Idempotency](https://docs.suprsend.com/reference/idempotent-requests) | **U:** the reviewed sources do not establish a precise managed Inbox storage/socket retry schedule or recovery SLA. The headless SDK exposes optional reachability status combining browser, socket and API checks; this diagnoses connection state, not guaranteed delivery. [Headless feed](https://docs.suprsend.com/docs/react-sdk-headless-feed) |

**I:** none of these finite idempotency windows makes a SQLite business commit and remote API call atomic. The later integration decision must cover durable event intent, stable retry keys, reconciling timeouts, and retries older than the provider window. No outbox implementation is selected here. API acceptance, stored feed item, client visibility, read state, and completed action should be separate acceptance criteria.

**I — data minimization:** send stable recipient/resource IDs, minimal summary text, and an authorized destination rather than full Refund Request reasons, financial records, or course data. SuprSend Extra Data is likewise exposed for frontend rendering. [Knock response content](https://docs.knock.app/integrations/in-app/feeds), [Novu payload](https://docs.novu.co/api-reference/events/trigger-event), [SuprSend Extra Data](https://docs.suprsend.com/docs/in-app-inbox-template)

**U for all providers:** actual contractual processing terms, subprocessors relevant to the chosen region, backup erasure latency, export completeness, and revocation of already displayed data have not been validated. Provider compliance statements are evidence to examine, not a determination that Cadence meets any legal obligation. Cadence's residency, permitted payloads, retention, deletion, and operational visibility requirements remain human decisions.

## Conditional disqualifiers and focused follow-up experiments

No candidate is unconditionally disqualified by the currently agreed scope. These are gates for the later provider decision, not additional requirements or resolved human choices:

1. **Recipient isolation:** reject any configuration that accepts another recipient's identity, read mutations, or tenant context. Test omitted/altered credentials, cross-account message IDs, sign-out, DevUI account switching, and removed team responsibility. Verify expiring JWT renewal (Knock/SuprSend); verify Novu hash/session revocation behavior rather than assuming the static subscriber HMAC expires.
2. **History and region:** if the chosen history exceeds a plan's feed retention, reject that plan or explicitly choose separate history. Confirm SuprSend unexpired retention. If EU-only processing is required immediately, do not count Knock's future roadmap as support. Validate account-region and deletion terms before selecting any provider.
3. **UI and SSR:** in an isolated technical spike after criteria are agreed, pin SDK versions, render the actual React Router SSR route, hydrate without errors, switch sessions, reconnect a socket, and follow an authorized action URL. Compare drop-in versus headless effort using Cadence's components. No provider has passed this test here.
4. **Accessibility:** test keyboard opening/closing, focus entry/return, notification and button names, unread-count announcements, non-color status cues, zoom, reduced motion, and screen-reader order. Request any provider audit/VPAT if needed. None was established in this review.
5. **Recovery and duplicates:** trigger the same event twice and concurrently; simulate a timeout after acceptance; reconnect after a missed socket update; retry after 24 hours; verify one intended feed item and consistent cross-tab read state. For Novu, confirm organization idempotency enablement before relying on the header. Investigate observability/reconciliation for failures, not just a successful demo.
6. **Stale actions and preferences:** test an already-resolved Refund Request, lost Enrollment, deleted resource, and changed audience responsibility. Decide whether links show current state, messages archive/replace, or expiry applies. Verify the actual paid/free preference entitlement and defaults against whichever notifications the human declares mandatory.

The provider-selection ticket still needs the event/audience matrix, expected monthly and peak load, budget, history expectations, permitted data/geography, required delivery behavior, and UI/accessibility criteria. Existing refund email delivery and transient toasts can coexist; this research does not authorize replacing them.
